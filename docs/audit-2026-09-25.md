## 2. Blockers — verified, act first

### B1. R2 sync is OOM-killed and slower than its own timer — **FIXED**

```
pow-r2-upload.service: The kernel OOM killer killed some processes in this unit.
pow-r2-upload.service: Failed with result 'oom-kill'.
kernel: Out of memory: Killed process 1969445 (python3) ... pow-r2-upload.service
```

Evidence: `journalctl --user -u pow-r2-upload` — kills at 18:57 and 18:59, plus
runs of 62–87 min against an hourly calendar timer; unit is `failed` right now.
`df`: 3.06 GiB free; raw growing ~14,000 files/hour.

**Why it matters:** local retention (`raw=24h`, `normalized=30h`) only executes
*inside* a successful run. Failed runs mean **no pruning**, so disk keeps
falling toward the 2 GiB `POW_MIN_FREE_BYTES` floor where collectors
self-pause. Backups and retention are currently on the same critical path.

**Fixed:** retention split into `pow-r2-retention.service/.timer` (own lock,
runs every 30 min even if the uploader fails) using the new `r2_upload.py
--prune` mode. Upload unit now has `MemoryHigh=512M` / `MemoryMax=768M` /
`OOMScoreAdjust=500`, workers 8 → 4. Timer switched to
`OnUnitInactiveSec=3600` so runs cannot overlap. Prune measured at **7 s**
(`kept=105,257 deleted=0` — nothing has aged past 24 h yet).

### B2. Monitoring reports success while a service is failed — **FIXED**

```
actual pow-r2-upload.service     failed
heartbeat sources_failed         0
heartbeat results                {..., "r2_sync": "ok", ...}
```

**Why it matters:** this is the exact failure mode `/powops` exists to prevent.
Root cause is in code written this session:

- `scripts/pipeline_status.py:285` — `elif not unit.endswith(".timer") and ...`
  exempts every timer-backed source from its unit-state check, so a dead timer
  service never propagates.
- `r2_sync` freshness is the **mtime of the R2 state file**, which is rewritten
  every 1,000 files even during a run that later dies — so a doomed run still
  looks fresh.

**Fixed:** `pipeline_status._unit_health()` resolves a timer to its service
and treats any `Result != success` as failure regardless of file freshness;
armed-timer state is checked too. `health_check.check_pipeline()` reads the
heartbeat's `sources_failed` and fails the 5-minute run, so a bad run turns
health red instead of green. Proven live: my own `systemctl stop` produced
`Result=signal`, health reported `pipeline:r2_sync`, exit 1.

### B3. The test suite writes into the live warehouse — **FIXED**

Counted directly:

```
run tests/test_garden.py once
trade rows with symbol "X":  34  ->  35
raw observations with endpoint="https://x": 35
```

Cause: `tests/test_garden.py:19-21` does `monkeypatch.setattr(core, 'BASE_DIR', tmp)`
on the **package** namespace, but `core/__init__.py:15-24` loads `core.py` as a
separate module and copies functions out — so `store_normalized.__globals__`
still points at the real repo. `tests/test_home.py:30` already uses the correct
pattern (`monkeypatch.setitem(fn.__globals__, ...)`).

**Why it matters:** test rows are indistinguishable from real trade rows,
they are R2-uploadable, and they are the direct cause of the one failing test.
Every green CI run silently degrades the dataset it is supposed to protect.

**Fix:** patch `core.store_normalized.__globals__` / `core._archive_raw.__globals__`
in the `isolated` fixture, then purge the35 polluted trade rows and the 35
`https://x` raw envelopes. *Effort: S. Dependency: none.*

## 3. High — correctness and honesty

### H1. `chains/network_state.json` co-writer race

Four writers read → mutate → write with **multi-second** windows using the
**same temp path**: `collectors/chain_state.py:63`, `collectors/qubic_stats.py:110`,
`scripts/qubic_epoch.py:137`, `scripts/qubic_computors.py:141`.
Two processes sharing `network_state.json.tmp` can interleave `json.dump`
(truncated file renamed into place) and silently drop each other's keys — the
QUBIC tick-quality fields written by `qubic_stats` are exactly what
`chain_state` can clobber.

Compounding it: `except OSError` around `json.load` misses
`json.JSONDecodeError` (a `ValueError`) at `chain_state.py:57`,
`site/server.py:655-659`, `site/server.py:775-778`, `factors.py:102-105`,
`signals.py:74-81`, `mcp_server.py:137-141` → one corrupt file becomes a
crash-loop (`Restart=always`) or dead endpoints.

**Fix:** a single `save_netstate()` helper writing to a per-PID temp file with
`os.replace`, plus `except (OSError, ValueError)` at every reader. *Effort: M.*

### H2. `ONBOARDING.md` is wrong about the system it says is verified

| Claim | Reality |

| `:51` — 5 enabled services | **7** (missing `pow-qubic-holdings`, `pow-qubic-transfers`) |

**Why it matters:** `ONBOARDING.md` is the entry point we just told every new
agent to trust. A wrong "verified, not aspirational" table is worse than no
table — it teaches the next agent to stop checking.

**Fix:** generate the counts (a small script that prints units / checks / test
total) or mark the table as a snapshot with a date. *Effort: S.*

### H3. Provenance claim vs practice

`docs/pow-systems-live.md:23` and `ONBOARDING.md:44` say every normalized row
carries `raw_event_id`. Of 66 `store_normalized` calls, **34 pass none**,
including live-path ones: `build_daily_state.py:205` (`daily_state`),
`signals.py:189,254,326` (`derived_signal`), `qubic_holdings.py:161`,
`chain_state.py:205,252,286,297`.

Derived rows being `NULL` is defensible; canonical rows are not. **Fix the doc
or thread the id** — pick one. *Effort: M for threading, S for the doc.*

### H4. Public subprocess fan-out with no rate limit

`GET /api/ops` and `GET /api/home` are ungated and each spawn up to **6
`systemctl` subprocesses with 5 s timeouts**, via an unbounded
`ThreadingHTTPServer`. `log_message` is suppressed (`site/server.py:863`), so
there is no access audit. `site/server.py:308,313-314` also still probes
`pow-venue-l2`, `pow-venue-ws` and `pow-pearld` — none of which exist.

**Fix:** cache `_ops()` for 60 s (already done for `/powops`, not for
`/api/ops`), drop the three dead units, and re-enable access logging for
non-2xx. *Effort: S.*
